# API Surface

The complete set of operations the dashboard performs. Two reads and seventeen writes — nothing
else. If a rebuild needs an eighteenth write, the feature is probably editing the plan, which this
page may not do.

The transport shown is this build's: HTTP under `/api/mgmt`, JSON in and out, served by a dev-only
plugin. **The transport is not the requirement** — a Rails project may serve these as controller
actions, a Go project as handlers. What is fixed is the operation set, the payloads, and the error
contract.

## Reads

| Operation | Returns |
|---|---|
| `GET /state` | The plan: project, phases, epics with tasks, blockers, metrics, readiness. Generated by `/setup` from `.idea/` |
| `GET /board` | Everything authored or synced: meta, authored tasks, assignees, task assignees, sprints, epic sprints, time entries, PRs, test runs, advances, parked criteria, priorities, statuses, pull requests |

Both are fetched together on load and re-fetched after **every** successful write. The page holds no
optimistic local model of derived state — see [[Derivations]].

> [!note] `pullRequests: null` means "no GitHub MCP configured"
> It does not mean "no open pull requests". The distinction is the whole point: an integration that
> is absent must read as absent, never as an empty result. See [[Requirements]].

## Writes

Each writes to `board.db` only. **None of them touches `.idea/`.**

| Operation | Payload | Notes |
|---|---|---|
| `POST /task` | `taskId, points, notes` | Points and free notes on any task |
| `POST /estimate` | `taskId, minutes` | Estimate only; actual is summed from time entries |
| `POST /time` | `taskId, minutes, note?` | Appends an entry. Never overwrites a total |
| `POST /assignee` | `name, handle?` | Adds a person |
| `POST /assign` | `taskId, assigneeId` | `null` unassigns |
| `POST /authored` | `title, epic, description?, priority?` | Creates an ad-hoc task, returns its `ADH-` id |
| `POST /authored/delete` | `taskId` | Only ad-hoc tasks can be deleted |
| `POST /authored/status` | `taskId, status` | Status of an ad-hoc task |
| `POST /status` | `taskId, status` | A drop, or the drawer's Move control. **`null` clears the override** |
| `POST /priority` | `taskId, priority` | `null` reverts to the phase-derived priority |
| `POST /pr` | `taskId, url` | Attaches a pull request |
| `POST /sprint` | `name, startsOn, endsOn, goal?` | End after start, no overlap, unique name |
| `POST /sprint/delete` | `sprintId` | |
| `POST /task/sprint` | `taskId, sprintId` | `null` removes from sprint |
| `POST /criterion/park` | `phase, text, parked` | Keyed by text, not index |
| `POST /phase/advance` | `phase, eligible, force, leftUnfinished?` | Returns `{ forced }` |
| `POST /phase/advance/withdraw` | `phase` | Steps back a pending advance |

**`null` is meaningful in three places** — clearing a status override, clearing a priority override,
and unassigning. Each reverts to the derived value rather than writing an opposite one. A rebuild
that treats `null` as "no change" silently breaks drag-back-to-origin.

## Error contract

Non-2xx responses carry `{ "error": "<human sentence>" }`. The client throws with that text, and the
drawer or board renders it inline.

> [!warning] A failed write is never silent
> The UI applies a write optimistically, then rolls back **visibly** with the server's message on
> failure. A board that quietly reverts a card looks like a drag that missed.

Validation belongs on the server, not only in the form: sprint dates, unique names, known status and
priority values, and existence of the referenced task.

## Exposure

The whole surface is **dev-only by default**. In this build the plugin mounts with `apply: 'serve'`,
so it does not exist in a production build at all — not a route that checks a flag, but a route that
was never compiled in.

Where a stack cannot express that, the equivalent is: mount the router only when the environment is
development, and fail closed if the environment cannot be determined. The gate the user picked at
`/setup` time (dev-only, auth-gated, or public) decides which of these applies.

A public roadmap of everything not yet built, plus your team's names and every blocker, should be a
deliberate choice. See [[Requirements]].
